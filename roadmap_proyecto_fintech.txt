INGRESO A - API DE TARJETAS (Datos sensibles) -> STREAMING
===============================================================================

[X] 1. Mock API FastAPI (api/mock_cards_api.py)
    - Servicio HTTP en puerto 8001 que simula la fuente externa de tarjetas.
    - Endpoint GET /cards?page=&page_size= paginado (~200 tarjetas mock),
      asociadas a user_id de la base.
    - Cada registro trae datos CRUDOS SENSIBLES:
        card_id, user_id, pan, cvv, exp_date, card_type, cardholder
    - Se corre con uvicorn (local, en el venv).
    Comando (ej.): ./venv/bin/uvicorn api.mock_cards_api:app --host 0.0.0.0 --port 8001

[X] 2. Ingestor (scripts/ingest_cards.py)
    - Llama a la API por páginas.
    - Aplica MASKING DE PII (práctica DE obligatoria en fintech / PCI-DSS):
        * pan        -> pan_last_masked (solo últimos 4, ej. **** **** **** 1234)
        * cvv        -> DESCARTADO (nunca se persiste)
        * cardholder -> enmascarado (ej. JUAN P. -> JU** P.)
    - Publica a un tópico Redpanda NUEVO: cards.api
    - Programado por cron (recurrente, ej. cada 5 min).

[X] 3. Worker ampliado (scripts/worker.py)
    - Refactor para leer de VARIOS tópicos o aceptar TOPIC/PREFIX por parámetro
      (hoy está hardcodeado a transactions).
    - Agregar suscripción a cards.api -> escribe Parquet en
        s3://fintech-lakehouse/cards/  (particionado por fecha).
    - Esquema Parquet de cards (SIN datos sensibles):
        card_id, user_id, pan_last_masked, card_type, cardholder_masked,
        exp_date, ingested_at

    RESULTADO: data sensible entra por API -> se ANONIMIZA en el ingest ->
    cae al lake como Parquet. El PAN/CVV plenos NUNCA llegan al lake.

FASE 3: DATA WAREHOUSE Y TRANSFORMACIONES DBT (ANALYTICS ENGINEERING FOCUS)
-------------------------------------------------------------------------------
[X] 3.1. Inicialización de dbt
    - dbt-postgres contra postgres_olap (5433) en dbt_fintech/.
    - profiles.yml (fintech_lakehouse) y dbt_project.yml configurados.
    - packages.yml -> dbt_expectations (vía `dbt deps`).
    - Bridge del lakehouse -> DW: scripts/load_lakehouse.py (Parquet/CSV de
      MinIO -> raw.* en postgres_olap; TRUNCATE + COPY, idempotente).
      (El anexo 8 lo dejaba en "solo landing"; con dbt-postgres el loader es
      el puente documentado.)

[X] 3.2. Capa Bronze / Staging (dbt)
    - stg_transactions.sql: casteo de tipos (amount NUMERIC), timestamps,
      dedup por id y renombrado snake_case.
    - stg_users.sql: estandarización (trim nombre, lower status_riesgo), dedup
      por último updated_at.
    - stg_cards.sql: tarjetas anonimizadas (sin PAN/CVV).
    - stg_card_movements.sql: movimientos del CSV diario (landing).

[X] 3.3. Capa Silver / Intermediate (SCD Type 2 & Reglas de Negocio)
    - dbt snapshot (snap_users_scoring) sobre usuarios: registra el historial
      de Scoring Crediticio a lo largo del tiempo (timestamp strategy).
      * worker.py ampliado: persiste postgres_oltp.public.users -> users/.
      * generator.py: ahora actualiza scoring/riesgo periódicamente para que
        el snapshot capture cambios reales.
    - int_user_transaction_velocity.sql: métricas en ventanas 5/15/60 min por
      usuario (macros count_tx / sum_tx).

[X] 3.4. Capa Gold / Marts (Modelado Dimensional Kimball)
    - dim_users.sql: dimensión de usuarios con estado actual e historial de
      scoring (is_current, valid_from/valid_to).
    - fct_transactions.sql: tabla de hechos transaccional unificada.
    - fct_fraud_alerts.sql: alertas por reglas:
        1) monto >= 5000
        2) monto > limite de crédito del usuario
        3) >= 5 transacciones del usuario en 5 min
        4) ubicación de la tx != ubicación del usuario
        5) bandera is_flagged_fraud de OLTP

[X] 3.5. Testing y Calidad de Datos
    - Tests primarios en schema.yml (unique, not_null).
    - dbt_expectations: expect_column_values_to_be_between (scoring 300-850,
      amount >= 0, cnt_5min >= 1) en intermediate/ y marts/.

EJECUCIÓN (orden sugerido):
